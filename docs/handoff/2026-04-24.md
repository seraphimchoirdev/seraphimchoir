## 3. Decisions Made (왜 그렇게 했는지)

### 3-1. 커서 페이지네이션 키를 `event_date` + `id`로 잡음
- 단순 `created_at desc`가 아닌 **행사 날짜 기준**이 사용자 멘탈모델에 맞음 (찬양대원은 "언제 부른 곡"으로 사진을 찾음).
- 같은 날짜에 여러 앨범이 있을 수 있어 `id` 보조 정렬로 안정성 확보.
- 커서는 `event_date` 하나만 직렬화 — 같은 날짜 앨범이 limit 경계에 걸리면 **중복 노출 가능성**이 미세하게 있음. 휴식 후 검토 포인트.

### 3-2. `quick-upload` 엔드포인트 분리
- 일반 사용자는 "앨범 만들기 → 사진 업로드" 2단계가 부담스러움.
- `/quick-upload`는 **현재 월(YYYY-MM) 자동 앨범**에 사진을 떨군다. 없으면 만들고, 있으면 추가.
- `useQuickUploadPhotos` 훅은 invalidate 대상이 3개(list/detail/photos) — 새 앨범이 생긴 케이스를 모두 커버하기 위함.

### 3-3. `enrichAlbums` 헬퍼로 N+1 제거
- 앨범 목록 + creator 정보 + event 정보를 별도 쿼리 2개로 묶음 (`Promise.all`).
- creator/event 둘 다 `Map`으로 lookup → O(N) 보장.
- DB 뷰로 옮길지 고민했으나, **앨범 수가 작고 RLS 정책 관리가 복잡해지므로** 애플리케이션 조립 유지.

### 3-4. `AlbumWithMeta`의 `cover_url`을 단순 path로
- Supabase Storage signed URL을 서버에서 만들어 내릴지, 클라이언트에서 publicUrl로 변환할지 고민.
- **현재는 path만 내려주고 클라이언트가 변환** (다른 커뮤니티 첨부와 일관성). 비공개 버킷으로 가야 한다면 여기를 갈아엎어야 함.
