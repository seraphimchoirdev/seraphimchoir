## 5. Decisions Made

| 결정사항 | 이유 / 근거 | 고려했으나 선택하지 않은 대안 |
|---------|------------|----------------------------|
| `service_schedule_id` FK를 NULL 허용으로 추가 | 기존 데이터 호환성 — 백필 실패 시 orphan 레코드 보존 | NOT NULL 강제 (데이터 손실 위험) |
| UNIQUE 변경: `(member_id, date)` → `(member_id, service_schedule_id)` | 같은 날 여러 예배 출석 기록 허용 | 복합키 `(member_id, date, service_schedule_id)` (과도한 복잡성) |
| 백필 시 '주일 2부 예배' 우선 매칭 | 실제 운영 데이터에서 주일 2부 예배가 가장 빈번 | 날짜만으로 단순 매칭 (다대다 충돌 위험) |
| `useAttendanceMode` 훅 분리 | 모드/잠금 로직이 여러 컴포넌트에서 재사용 가능 | AttendanceList 내부에 인라인 구현 |
| API에서 `service_schedule_id` 없을 때 `date` 폴백 | 하위 호환 — 이전 클라이언트도 동작 | 즉시 breaking change |

## 8. Patterns & Conventions

- **예배별 출석 키**: 기존 `(member_id, date)` → `(member_id, service_schedule_id)` 패턴 전환
- **하위 호환 API**: `service_schedule_id`가 없으면 `date`로 폴백하는 패턴 (batch, arrangements 모두)
- **모드 패턴**: `useAttendanceMode` 훅으로 시간/역할 기반 UI 모드 결정
  - `service-entry`: 주중 (예배 등단 투표)
  - `practice`: 주일 당일 09:00 이후 (연습 출석)
  - `both`: ADMIN/CONDUCTOR (모든 탭 접근)
- **백필 전략**: 주일 2부 예배 우선 → 날짜 매칭 → 첫 번째 schedule 순서

## 9. Potential Gotchas

- ⚠️ 마이그레이션에서 `DROP CONSTRAINT ... attendances_member_id_date_key`가 실행되므로, 기존 `(member_id, date)` 유니크 제약에 의존하는 코드가 있으면 깨질 수 있음
- ⚠️ `service_schedule_id`가 NULL인 출석 레코드는 새 UNIQUE 제약에 참여하지 않음 (PostgreSQL NULL 특성) — 같은 member가 NULL schedule에 대해 여러 레코드를 가질 수 있음
- ⚠️ `my-attendance/page.tsx`에서 `useEffect`로 첫 번째 예배 자동 펼침 처리하는데, 상태 경합 가능성 확인 필요
- ⚠️ staged 변경이 12개 파일로 대규모 — 하나의 커밋으로 합치기보다 기능 단위로 분리 커밋을 고려할 것
- ⚠️ `database.types.ts` 변경이 +343라인인데, Supabase CLI `gen types`로 재생성한 것인지 수동 편집인지 확인 필요
