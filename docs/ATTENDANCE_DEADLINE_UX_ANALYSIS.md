# 출석 마감 기능 UX 분석

> **문서 목적**: 출석 마감 기능의 현재 구현을 분석하고, UX 문제점을 파악하여 개선 방향을 제시합니다.
> **현재 상태**: 프론트엔드에서 비활성화됨 (API/DB/훅은 보존)
> **작성일**: 2026-01-31

---

## 1. 기능 개요

출석 마감(Attendance Deadline)은 특정 날짜의 출석 데이터가 확정되었음을 표시하는 잠금 메커니즘입니다.

### 워크플로우

```
파트별 출석 입력 → 파트별 마감 → 전체 마감 → 자리배치표 생성
```

### 마감 종류

| 종류 | DB 표현 | 의미 |
|------|---------|------|
| 파트 마감 | `part = 'SOPRANO'` 등 | 해당 파트의 출석이 확정됨 |
| 전체 마감 | `part = NULL` | 모든 파트 출석이 확정됨 |

### 권한 모델

| 역할 | 파트 마감 | 전체 마감 | 마감 해제 |
|------|----------|----------|----------|
| PART_LEADER | 본인 파트만 | X | X |
| MANAGER | 모든 파트 | X | X |
| CONDUCTOR | 모든 파트 | O | O |
| ADMIN | 모든 파트 | O | O |

## 2. 현재 구현의 UX 문제점

### 2.1 마감 개념의 불명확성

**문제**: "마감"이라는 단어가 사용자에게 어떤 의미인지 직관적이지 않습니다.

- 파트장 입장에서 "마감 버튼을 누르면 어떻게 되는가?"가 명확하지 않음
- 마감 후에도 수정이 필요한 상황(예: 늦은 연락, 오입력)에 대한 가이드 부족
- "마감 해제"가 CONDUCTOR/ADMIN만 가능하다는 사실을 미리 알기 어려움

**실제 시나리오**:
> 파트장 A가 소프라노 파트를 마감한 후, 대원 B에게서 "불참이 아니라 참석이에요"라는 메시지를 받음.
> → 파트장 A는 마감을 해제할 수 없어 지휘자에게 연락해야 함
> → 지휘자가 바쁘면 수정이 지연됨

### 2.2 잠금(Lock) UX의 답답함

**문제**: 마감 후 UI가 비활성화되면 사용자가 "왜 클릭이 안 되지?"라고 혼란을 느낍니다.

- `MemberChip`이 `disabled`로 변경되지만 시각적 피드백이 미묘함
- 마감 안내 메시지("이 파트는 마감되어 수정할 수 없습니다")가 작고 눈에 띄지 않음
- 저장 버튼이 "마감된 파트의 N건은 저장되지 않습니다" 경고를 보여주지만, 이미 변경한 후에야 인지함

### 2.3 파트 마감 → 전체 마감의 2단계 구조

**문제**: 파트별 마감과 전체 마감의 관계가 직관적이지 않습니다.

- 모든 파트가 마감되어야 전체 마감 버튼이 나타남
- 왜 파트별로 따로 마감해야 하는지에 대한 설명 부족
- 전체 마감의 필요성이 불명확 (자리배치와의 연관성을 모르면 의미 없음)

### 2.4 DeadlineStatusBar의 복잡성

**문제**: 5개 파트의 마감 상태를 한 줄에 표시하려다 보니 정보 밀도가 높습니다.

현재 구현:
```
[🔓 출석 마감 현황] [S✓] [A✓] [T ] [B ] [SP ] [전체 마감]
```

- 모바일에서 공간 부족으로 가독성 저하
- 클릭 가능한 요소와 상태 표시 요소의 구분이 어려움
- 파트 약어(S, A, T, B, SP)가 새 사용자에게 직관적이지 않을 수 있음

### 2.5 되돌리기 불가능한 상황

**문제**: 자리배치표가 생성된 후에는 마감 해제가 불가능합니다.

- DELETE `/api/attendances/deadlines/[id]`에서 자리배치 존재 시 409 반환
- 이 제한의 이유(데이터 정합성)가 사용자에게 설명되지 않음
- 급한 수정이 필요할 때 해결 방법이 없음

## 3. 실제 사용 패턴 분석

### 주간 출석 워크플로우 (현장 관찰 기반)

```
[월~토] 파트장들이 카카오톡으로 출석 여부 확인
[토]    파트장들이 앱에 출석 입력
[토]    지휘자가 전체 확인 후 자리배치 생성
[일]    예배 당일 변경사항 발생 가능
```

### 핵심 관찰

1. **출석 확정 시점이 유동적**: 토요일에 입력해도 일요일 오전까지 변경 가능성 있음
2. **마감의 실질적 의미**: "더 이상 변경하지 않겠다"보다 "자리배치 생성 준비 완료"에 가까움
3. **파트장 간 시차**: 모든 파트장이 동시에 입력을 완료하지 않음 → 파트별 마감은 진행 상황 추적에 유용

## 4. 개선 제안

### Option A: "마감"을 "확인 완료"로 재정의

**핵심 변경**: 잠금이 아닌 상태 표시로 전환

```
기존: 마감 → 수정 불가 → 해제 필요
개선: 확인 완료 표시 → 수정은 여전히 가능 → 자리배치 생성 시에만 잠금
```

- 파트장이 "확인 완료" 표시를 해도 출석 수정은 가능
- 지휘자는 모든 파트가 "확인 완료"인지 한눈에 확인
- 자리배치 생성 시점에 최종 잠금 (이 시점에서만 경고)

**장점**: 파트장의 부담 감소, 지휘자의 워크플로우 유지
**단점**: "확인 완료했는데 왜 바뀌었지?" 혼란 가능

### Option B: 마감은 유지하되 "임시 수정" 허용

```
마감 후에도 수정 가능 → 단, "마감 후 수정됨" 표시
지휘자가 최종 확인 시 변경 이력 볼 수 있음
```

- 파트장이 마감 후에도 수정 가능 (하지만 변경 기록 남음)
- 지휘자에게 "마감 후 수정 있음" 알림
- 자리배치 생성 전 지휘자가 변경사항 확인/승인

**장점**: 유연성과 추적 가능성 동시 확보
**단점**: 구현 복잡도 증가, 알림 시스템 필요

### Option C: 마감 자체를 제거하고 자리배치 연동으로 대체

```
출석 입력 → (마감 없음) → 자리배치 생성 시 출석 스냅샷 저장
자리배치 생성 후에만 수정 제한
```

- 마감이라는 별도 단계 제거
- 자리배치 생성 시 해당 시점의 출석 데이터를 스냅샷으로 저장
- 자리배치 생성 후 출석 수정 시 "자리배치와 불일치" 경고만 표시

**장점**: 가장 단순한 UX, 불필요한 단계 제거
**단점**: 파트장별 진행 상황 추적 기능 상실

### Option D (권장): 파트별 "준비 완료" + 자리배치 생성 시 잠금

Option A + C의 혼합:

```
파트장 → "준비 완료" 표시 (수정은 가능)
지휘자 → 모든 파트 준비 완료 확인 → 자리배치 생성
자리배치 생성 시점에 출석 잠금 + 스냅샷
```

- **파트장**: "준비 완료" 버튼 (부담 없음, 언제든 해제 가능)
- **지휘자**: 대시보드에서 파트별 준비 상태 확인
- **잠금 시점**: 자리배치 생성 시에만 발생 (명확한 이유)
- **UI**: `DeadlineStatusBar` → `ReadinessBar`로 전환

**장점**:
- 마감의 실질적 목적(자리배치 준비)에 맞는 워크플로우
- 파트장의 심리적 부담 감소 ("마감" vs "준비 완료")
- 진행 상황 추적 기능 유지

## 6. 기술적 영향도

### 보존된 인프라 (재활용 가능)

| 요소 | 파일 | 재활용 방법 |
|------|------|-------------|
| DB 테이블 | `attendance_deadlines` | "준비 완료" 데이터로 재해석 |
| API (조회) | `GET /api/attendances/deadlines` | 그대로 사용 |
| API (생성) | `POST /api/attendances/deadlines` | 잠금 없이 상태 표시만 |
| API (해제) | `DELETE /api/attendances/deadlines/[id]` | 파트장도 해제 가능하도록 권한 수정 |
| 훅 | `useAttendanceDeadlines` | 변수명만 변경 (deadline → readiness) |
| 컴포넌트 | `DeadlineStatusBar` | `ReadinessBar`로 리팩토링 |

### 수정이 필요한 부분

1. **RLS 정책**: DELETE 권한을 PART_LEADER까지 확장
2. **UI 컴포넌트**: 잠금 아이콘 → 체크 아이콘, 색상 변경
3. **클라이언트 로직**: `disabled` 제거, "준비 완료" 상태는 정보 표시만
4. **자리배치 생성 로직**: 생성 시 출석 스냅샷 저장 추가

---

## 7. 결론

현재 마감 기능은 **기술적으로는 잘 구현**되어 있으나, **UX 관점에서 "마감 = 잠금"이라는 엄격한 모델이 실제 사용 패턴과 맞지 않습니다.**

핵심 인사이트:
- 찬양대 출석은 **유동적**이며, 예배 직전까지 변경 가능
- 마감의 실질적 목적은 **자리배치 생성 준비 확인**
- 파트장에게 "되돌릴 수 없는 결정"을 요구하는 것은 심리적 부담

**권장 방향**: Option D (파트별 준비 완료 + 자리배치 생성 시 잠금)로 전환하여, 기존 인프라를 재활용하면서 더 자연스러운 워크플로우를 제공합니다.
